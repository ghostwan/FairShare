# FairShare — Multi-device sync design

Status: shipped through step L; post-L follow-ups in §10.
Branch: `share`
Owner decision (recap): CRDT engine + dual transport (Sneakernet for
offline / Cloudflare Worker for online), end-to-end encrypted, with
auto-selection at runtime. Phase 1 ships CRDT + Sneakernet; phase 2
adds the Worker.

## 1. Goals & non-goals

### Goals

- Multiple devices can edit the same Event (participants, expenses,
  receipts) and converge to the same state without a central server
  arbitrating writes.
- Works fully offline: a user can hand off changes via Share Intent,
  copyable link, or QR code (the "sneakernet" transport).
- Works online when a Cloudflare Worker is reachable: changes are
  pushed/pulled automatically.
- Zero-knowledge backend: the Worker stores opaque encrypted blobs.
  Losing the Worker DB does not leak any expense data.
- Atomic per-Event: each Event has its own keypair and op log. Joining
  an Event is a single URL/QR scan.

### Non-goals (v1)

- Per-field collaboration inside a single Expense. An Expense is the
  smallest mergeable unit; concurrent edits on the same Expense resolve
  via Last-Writer-Wins (LWW) at Expense granularity.
- User accounts, authentication, friend graphs. The invitation link
  carries everything needed to join.
- History/audit UI. The op log is an implementation detail; the user
  sees the materialized state only.
- Migration of existing local data: dev-only `fallbackToDestructive
  Migration` is kept; bumping the schema wipes the DB.

## 2. Identity model

### 2.1 IDs

All persisted domain entities switch from `Long` autogenerated by Room
to `String` UUID v4 generated client-side at creation time:

- `Event.id`
- `Participant.id`
- `Expense.id`
- `ExpenseShare.id`
- `ExpenseItem.id`
- `ExpenseItemAssignment.id` (if kept; currently no PK)

`ReceiptItem.id` is already a `String` UUID (transient, not persisted)
— unchanged.

Rationale: op-based CRDTs require globally unique IDs assigned at the
origin device. Otherwise two devices creating "Expense #5" would
collide.

Migration: destructive (DB version bump, wipe). The app is dev-only.

### 2.2 DeviceId

Each install generates a UUID v4 the first time the app launches and
persists it in DataStore (`device_id` key). It is not user-visible. It
is used:

- As a tiebreaker in LWW comparisons (see §4.2).
- As the `deviceId` field stamped on every emitted Op.

### 2.3 Event encryption key

Created together with the Event, on the originating device:

- 256-bit random key, AES-GCM.
- Stored locally in `EventEntity` (`encryption_key` BLOB column).
- Shared out-of-band via the invitation URL / QR (see §6.1).

The key never leaves the device except inside an invitation. It is
not stored on the Worker. Two different Events have two different keys.

## 3. Operation log

### 3.1 Op envelope

```kotlin
data class Operation(
    val opId: String,              // UUID v4, generated at emit time
    val eventId: String,           // scopes the op to one event
    val deviceId: String,          // emitter device
    val lamport: Long,             // see §4.1
    val wallClockMs: Long,         // best-effort wall clock, debug only
    val payload: OpPayload,        // sealed, see §3.2
)
```

Ops are immutable. Once emitted they are appended to the local log and
never rewritten. They are the canonical source of truth; the Room
tables for Event/Participant/Expense are a derived materialized view.

### 3.2 Op payload types (sealed)

```kotlin
sealed interface OpPayload {
    // Event
    data class EventUpsert(val event: EventSnapshot) : OpPayload
    data class EventDelete(val eventId: String) : OpPayload

    // Participant
    data class ParticipantUpsert(val participant: ParticipantSnapshot) : OpPayload
    data class ParticipantDelete(val participantId: String) : OpPayload

    // Expense (atomic: includes shares + items)
    data class ExpenseUpsert(val expense: ExpenseSnapshot) : OpPayload
    data class ExpenseDelete(val expenseId: String) : OpPayload
}
```

Snapshot types mirror the domain models but are pure data, versioned by
the sealed hierarchy (additive-only changes). One Expense op carries
the whole tree (shares + items + assignments) — the chosen granularity.

### 3.3 Storage

New Room table `operations`:

```
operations (
  op_id        TEXT PRIMARY KEY,
  event_id     TEXT NOT NULL,
  device_id    TEXT NOT NULL,
  lamport      INTEGER NOT NULL,
  wall_clock_ms INTEGER NOT NULL,
  payload_json TEXT NOT NULL,        -- serialized OpPayload
  applied      INTEGER NOT NULL,     -- 0/1, set after materializer runs
  origin       TEXT NOT NULL         -- LOCAL | SNEAKERNET | CLOUD
)
INDEX (event_id, lamport)
INDEX (event_id, applied)
```

The op log is append-only. Apps never delete from it (except a future
compaction job, out of v1 scope).

## 4. Convergence semantics

### 4.1 Lamport clock

Per-device monotonic counter persisted in DataStore (`lamport_clock`).

- On local emit: `lamport = ++local`
- On receive: `local = max(local, received.lamport); lamport_received`
  is preserved on the stored op.
- Comparison: `(lamport, deviceId)` lexicographic ordering ensures total
  order across the cluster without coordination.

### 4.2 Conflict resolution

Per entity (Event, Participant, Expense), the materializer keeps the op
with the highest `(lamport, deviceId)` for that `entityId` among ops of
the same family (Upsert vs Delete).

- **Delete-wins-on-tie within the same entity is not used.** A later
  Upsert overrides an earlier Delete. Rationale: undo by re-create is
  intuitive; tombstones are kept only to suppress earlier Upserts.
- **Add-wins for set membership**: an Event's participant set is the
  set of participants with a surviving Upsert.

This is LWW at entity granularity, applied independently per entity
type. It is well-known to converge; no extra causality tracking needed
beyond the Lamport pair.

### 4.3 Materializer

`OperationApplier` (data layer) takes an op (or a batch), and:

1. Inserts it into `operations` (idempotent: `opId` PK).
2. For each affected entity, recomputes the winning op from the log
   and writes the resulting state into the materialized tables
   (`events`, `participants`, `expenses`, `expense_shares`,
   `expense_items`, `expense_item_assignments`).
3. Marks ops `applied = 1`.

The materializer is deterministic and idempotent. Replaying the log on
a wiped DB yields the same materialized state.

## 5. Refactor of the write path

Today repos call DAOs directly. They will be rewritten to:

1. Build an `Operation` describing the intent.
2. Hand it to `OperationApplier.applyLocal(op)`, which appends to the
   log, materializes, and notifies the active transports.

`ExpenseDao.upsertWithDetails` (delete-then-insert) is replaced by a
diff-aware applier that only touches shares/items whose snapshot
changed. This is required because concurrent merges must not destroy
the entire shares/items set when a single field changes.

ViewModels keep calling the same repository APIs; signatures only
change from `Long` to `String` for IDs.

## 6. Transports

### 6.1 Sneakernet (phase 1)

A bundle of ops is encoded as:

```
fairshare://sync?event=<eventId>&data=<base64url(gzip(json(ops)))>
                &sig=<hmac>           # MAC over data, key from event key
```

Encoded into:

- **Share Intent** (`ACTION_SEND`, `text/plain`): user picks WhatsApp,
  Signal, mail, etc.
- **Copy link** button.
- **QR code** (Compose canvas, ZXing).

Receiving side: `intent-filter` on `fairshare` scheme + dedicated
"Apply changes" screen for pasted links / scanned QR. On apply:
decrypt, verify HMAC, hand each op to `OperationApplier`.

Invitation link variant carries the encryption key:

```
fairshare://join?event=<eventId>&name=<urlencoded>&key=<base64url(32 bytes)>
                 &seed=<base64url(initial-ops-bundle)>
```

`seed` is the initial export (event creation + initial participants),
so a fresh device can bootstrap from a single scan.

### 6.2 Cloud (phase 2)

Cloudflare Worker with D1:

```
ops (
  event_id    TEXT NOT NULL,
  op_id       TEXT PRIMARY KEY,
  lamport     INTEGER NOT NULL,
  device_id   TEXT NOT NULL,
  ciphertext  BLOB NOT NULL,         -- AES-GCM(op envelope)
  nonce       BLOB NOT NULL,
  received_at INTEGER NOT NULL
)
INDEX (event_id, lamport)
```

Endpoints (actual, see `worker/src/index.ts`):

- `POST /events/{eventId}/ops` — push a batch of `{opId, lamport,
  deviceId, nonce, ciphertext}`. Idempotent (opId is PK). Empty
  `ops` is allowed and used as a no-op handshake to register the
  bearer (see §6.4).
- `GET /events/{eventId}/ops?since=N` — pull ops with `lamport > N`.
  Bounded page size (500); response includes `nextSince` + `hasMore`.

The Worker performs no decryption and stores no plaintext. Auth is by
event-scoped HMAC token (derived from the event key) so random people
can't enumerate events.

#### 6.4 Bearer registration (register-on-first-use)

The Worker has no concept of "create event" — events come into
existence the first time a device proves it knows the event key by
sending a valid bearer over `POST /events/{eventId}/ops`. From that
point on, every subsequent request (push or pull) must present the
*same* bearer.

This is enforced in `checkBearer` (`worker/src/index.ts`):

- Unknown event + `POST` → register the presented bearer, accept.
- Unknown event + `GET` → reject with 401 `unknown_event`.
- Known event + matching bearer → accept.
- Known event + different bearer → reject with 401 `bad_bearer`.

Client-side (`SyncCoordinator.syncEvent`) implications:

1. **Push always runs before pull.** Pulling first on a freshly
   joined event would 401, throw, and never reach the push that
   would have registered the bearer — leading to an infinite
   WorkManager retry loop. The order is push → pull.
2. **First sync always POSTs**, even with no local ops to send.
   `CloudCursorStore.isBearerRegistered(eventId)` persists whether
   the empty-ops handshake has succeeded; subsequent syncs skip the
   empty POST when there's nothing to push.
3. **`unknown_event` on pull is non-fatal.** We treat it as "nothing
   to pull yet" and let the next sync cycle retry, defending against
   races where the push hasn't propagated to the D1 read replica.

Net result: a device that joins an event via sneakernet but has not
emitted any local op will still announce itself to the Worker on the
next foreground sync, and will receive all cloud ops on the cycle
after that.

In-app sync runs as a `WorkManager` periodic job + manual pull-to-
refresh + push on every local op.

### 6.3 Auto-selection

A single `SyncCoordinator` registers all available transports. On every
local op, it pushes via every available transport. On startup and on
network change, it pulls from the cloud transport if reachable.
Sneakernet is "passive" (no push), only invoked when the user explicitly
exports.

## 7. Cryptography details

- Algorithm: AES-256-GCM. 12-byte random nonce per ciphertext. 16-byte
  tag.
- Key derivation: none. The 32-byte event key is used directly.
- HMAC for Sneakernet integrity: HMAC-SHA256 over the base64url
  `data` parameter, key = first 32 bytes of `HKDF(eventKey, "fairshare
  -sneakernet-mac")`.
- Worker auth token: HMAC-SHA256 over `eventId`, key = `HKDF(eventKey,
  "fairshare-worker-auth")`. Sent as `Authorization: Bearer <token>`.
- All implementations use platform primitives: `javax.crypto.Cipher`
  for AES-GCM, `javax.crypto.Mac` for HMAC.

## 8. Breaking changes summary

- DB schema version bumped, destructive migration. Existing dev data
  is lost on update.
- All entity primary keys change from `Long` to `String`.
- Domain models, repository signatures, use case signatures, and
  ViewModels updated accordingly. ~12 call sites.
- `ExpenseRepository.upsertWithDetails` semantics change from
  "replace shares/items" to "diff and apply".

## 9. Test strategy

- Existing 23 OCR/parser tests stay green throughout. They don't touch
  the persistence layer.
- New CRDT property tests (JVM, no Android):
  - **Idempotency**: applying the same op twice yields the same state.
  - **Commutativity**: applying ops in any order yields the same state.
  - **Convergence**: two simulated devices emitting interleaved ops
    converge once they sync.
  - **Delete + late Upsert**: later Upsert wins.
  - **LWW tiebreaker**: identical lamport, different deviceId, lexico
    deviceId wins.
- Sneakernet round-trip test: encode → decode → identical op set.
- Crypto round-trip test for AES-GCM and HMAC helpers.
